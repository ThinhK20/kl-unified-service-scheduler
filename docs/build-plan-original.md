Unified Service Scheduler – Build Plan · OverviewWe build a web app where a customer books a car service, and the system makes sure a qualified technician and a free service bay are both available for the whole job. Double booking must be impossible, even when many people book at the same second.Goals- - A customer picks a vehicle, a service type, a dealership and a start time.- The system checks that one technician and one bay are free for the full duration.- On success, it saves an Appointment that links customer, vehicle, technician and bay.- The database itself blocks double booking (unique slot rows on a 15-minute grid).In scope- - Backend REST API (.NET + Entity Framework Core + SQL Server).- Frontend (React + TypeScript): book an appointment, see available times, see and cancel bookings.- Seed data for dealerships, technicians, bays and service types.- Unit, integration and concurrency tests.Out of scope (mentioned in README only)- - Login and user accounts (we use a fixed demo customer).- Email or SMS notifications.- Rescheduling, jobs that need two technicians, payment.Tech stackWe use .NET 8 with EF Core and SQL Server on the backend, and React with TypeScript on the frontend.PartChoiceWhyAPIASP.NET Core 8 Web API (controllers)Standard, well known, easy for reviewers to readData accessEntity Framework Core 8Required by the task; migrations and LINQDatabaseSQL Server (Docker container)Supports UNIQUE constraints and transactions we needValidationFluentValidationKeeps validation rules out of controllersTests (backend)xUnit, FluentAssertions, TestcontainersReal SQL Server in tests, so concurrency tests are honestFrontendReact 18 + TypeScript + ViteFast setup, typed codeServer stateTanStack QueryCaching, loading and error states for API callsFormsReact Hook Form + ZodTyped forms with simple validationTests (frontend)Vitest + React Testing LibraryFast, works with ViteRun everythingDocker ComposeOne command: database + API + webArchitectureThe backend uses Clean Architecture: four layers, and each layer only depends on the layers inside it. Booking flowA booking tries free technician + bay pairs one by one; the database's UNIQUE rule decides the winner when two people race for the same slot.A "slot taken" error is not a failure of the request; it only means another booking won that pair, so we move to the next one.- - Validate the request. Vehicle belongs to the customer, service type exists, start time is on the 15-minute grid and in the future.- Check idempotency key. We hash the request body. Same key and same hash: return the saved response again (no new booking). Same key but a different hash: return 409 IDEMPOTENCY_CONFLICT.- Work out the time range. End = start + service duration. Check the whole range is inside dealership opening hours.- Find candidates.- - Active technicians at this dealership, with the required skill at or above the minimum tier, whose shift covers the whole range, and with no slot rows in the range.- Active bays at this dealership, with the required bay type, and with no slot rows in the range.- Order candidates using the allocation strategy (default: the least-qualified technician who can still do the job, then the least busy that day; the simplest suitable bay). This keeps senior technicians free for hard jobs.- Try to save for the first pair: insert the Appointment (with its rule snapshots), all its ResourceSlots rows and the idempotency record in one transaction.- If the database says "duplicate" (SQL error 2601 or 2627), someone else just took that slot. Roll back, clear the change tracker, and try the next pair.- If a save succeeds, return 201 Created with the appointment.- If no pair works, return 409 Conflict with up to 3 nearby free start times as suggestions.Step 4 is only a fast filter. Safer (the database blocks overlaps even if code has a bug) and no deadlocks, but start times must be on a 15-minute grid and there are more rows. Row locking was the alternative; it allows any time but depends on every code path remembering to lock.- No MediatR. Fewer dependencies; we lose its pipeline features, which we do not need here.- Availability is a hint, not a promise. The free times list can change a second later; the booking call is the real check.Ideas from a similar project (- tuhdo/kl_unified_scheduler_scenario_a, Python + PostgreSQL)- - Taken: idempotency request hash, saving the response with the key, least-qualified-first technician choice with tiers, rule snapshots on the appointment, active flags, stable error codes, architecture tests, health checks, a curl walkthrough in the README.- Confirmed: the database should be the final judge of overlaps (they use a PostgreSQL exclusion constraint; we use unique slots), and a fixed time grid is normal (theirs is 60 minutes, ours is 15).- Not copied: two database adapters (SQLite + PostgreSQL), Jaeger tracing, the large spec and work-item process, accepting both camelCase and snake_case.- Maybe later: an optional latestFinish on the request, so the system books the earliest free slot in a window instead of returning 409.Open questions- - Decided: no login, a demo customer is enough.- Should the customer be able to choose a technician, or does the system always choose?- Is there a time limit for the assignment, so we can cut phase 6 or 7 if needed?
